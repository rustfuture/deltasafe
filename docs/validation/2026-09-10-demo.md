the listed environment and scenarios, not a production security certification.

## Automated checks

The suite reported 14 library tests, 5 integration tests, 5 helper tests, and 1 doctest, all passing with
the committed lockfile. The integration tests cover nested and multi-chunk files, empty files, password
salt exchange, wrong passwords, existing destinations, corrupt ciphertext, truncated frames, path
traversal, and symlink-parent rejection.

## Demo harness

`scripts/demo_loopback.sh` builds the current checkout with `cargo build --locked`, records the commit,
dirty-file count, and binary SHA-256, then:

1. Creates an owned `mktemp -d` working root with separate source and receiver directories.
2. Picks a free loopback port and runs the receiver from the owned receive root (its working directory),
   so it writes under a fresh `received_files/` instead of the repository tree.
3. Waits for readiness by polling an actual TCP connect while checking the receiver process is alive.
   A fixed sleep or connecting to another process's port is never accepted as readiness.
4. Sends a wrong password of valid length (17 characters) and requires the sender to fail while publishing
   no destination file.
5. Sends the correct password and verifies byte-for-byte `cmp` equality for an empty file, a small text
   file, and a nested 20000-byte (multi-frame) binary.
6. Stops only its own receiver process and removes only its own temporary root.

Two independent clean runs passed:

- `reports/demos/deltasafe-demo-run1-2026-09-10.txt`
- `reports/demos/deltasafe-demo-run2-2026-09-10.txt`

Both reported `DEMO PASS`, the same binary SHA-256, and verified all three files.

## Controlled startup failure

Running the harness with `DELTASAFE_DEMO_ADDR=192.0.2.1:12345` (an address that cannot bind locally) made
the receiver exit before readiness. The harness reported `FAIL: receiver exited before becoming ready`,
included the receiver log, and exited non-zero. See
`reports/demos/deltasafe-demo-startup-failure-2026-09-10.txt`. This shows the harness fails when startup
fails rather than reporting a false pass.

## Boundaries

- The demo is loopback only; it is not a cross-device test.
- Passing tests and this demo are evidence for the listed scenarios only. They do not claim
  certificate-based device identity, TLS, forward secrecy, durable replay protection across receiver
  restarts, or elimination of TOCTOU races against a hostile local process.
- Refusing to publish unverified or partial files is distinct from preventing every local filesystem race;
  the latter is not claimed.
